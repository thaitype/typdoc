# 5: v0.3.0 release readiness — crate metadata, version bumps, crates.io publish workflow

Type: implementation
Status: open
Blocked by: 1, 2, 3, 4 (decided 2026-09-24 — hard dependency, not a landing-order suggestion:
CHANGELOG, the skill's version line, and README all need to describe what 1-4 actually shipped;
writing them before those land is guessing)

## What this delivers

The repo is ready to publish `typdoc-core`, `typdoc-fs`, `typdoc` 0.3.0 to crates.io. Demoable:
this ticket's own PR shows a green `publish-check` run (the dry-run gate) alongside `ci.yml`'s
existing jobs still running in full. The real publish itself is explicitly **not** part of this
ticket — it is triggered separately, after merge.

## Scope (contract §4 + §5)

### Crate metadata
`[workspace.package]` in the root `Cargo.toml` gains `license = "MIT"` and `repository =
"https://github.com/thaitype/typdoc"`, inherited (`license.workspace = true`,
`repository.workspace = true`) by `typdoc-core`, `typdoc-fs`, `typdoc`, `typdoc-testkit`.
`description` is **not** inherited — each published crate sets its own:
- `typdoc-core`: "Reads a typdoc project and answers questions about it. It changes nothing."
- `typdoc-fs`: "The write half of the seam: the file system itself."
- `typdoc`: "A CLI that treats a folder of Markdown files as typed, linked documents."

### Version bumps
- `version` → `0.3.0` in all four crates' `Cargo.toml` (including `typdoc-testkit`, for workspace
  parity — it's unpublished either way).
- Every intra-workspace dependency requirement currently pinned `"0.2.0"` (`typdoc-fs`'s and
  `typdoc`'s `typdoc-core = { version = "0.2.0", ... }`, `typdoc`'s `typdoc-fs` requirement) →
  `"0.3.0"`. Load-bearing: a stale requirement fails the workspace build outright, which is what
  makes the publish workflow's version-check step meaningful rather than redundant.
- CHANGELOG entry for v0.3.0 (match the existing file's established format).
- Skill's version line (currently states 0.2.0) → 0.3.0.
- README's tag-based install instructions → reference the new tag.
- No git tag created by this ticket — tagging happens separately after merge + real publish.

### Publish workflows — two files, not one (contract §4's "Revised" note — read it, the reasoning
matters: `workflow_dispatch` only runs a workflow already on the default branch, so a single
`workflow_dispatch`-gated file can't produce gate evidence on this story's own PR branch)

1. **New `.github/workflows/publish-check.yml`** — its own file, not a job inside `ci.yml`
   (a `paths:` filter is workflow-level in GitHub Actions, not job-level; putting this job inside
   `ci.yml` would stop `test`/`fmt`/`clippy` running on any PR that doesn't touch a manifest).
   `on: push, pull_request: branches: [main]`, `paths:` scoped to `Cargo.toml`, `Cargo.lock`,
   `crates/*/Cargo.toml`. One job, `publish-dry-run`, ubuntu-latest + macos-latest matrix,
   running `cargo publish --workspace --dry-run`. No token. The path filter exists so that, after
   the real v0.3.0 publish, an unrelated later PR that hasn't bumped versions doesn't re-run a
   dry-run against an already-published version on every push.
2. **New `.github/workflows/publish.yml`**, `workflow_dispatch` only — `version` (required text)
   + `dry_run` (boolean, default `true`) inputs, modeled on
   `~/gits/thaitype/reeve/.github/workflows/publish.yml`. Its own `gate` job (ubuntu+macos `cargo
   test` + `cargo clippy --workspace --all-targets -- -D warnings`), a version-check step
   covering **all three** published crates' `Cargo.toml` versions against the input, then `cargo
   publish --workspace --dry-run` and (real run only, gated on `dry_run == false`) `cargo publish
   --workspace` with `CARGO_REGISTRY_TOKEN`. `cargo publish --workspace` is confirmed available
   on the pinned toolchain (`cargo 1.96.0`) and publishes in dependency order itself, skipping
   `typdoc-testkit` automatically (`publish = false`) — no manual per-crate `needs:` chain. No
   `release-binaries` job (out of scope this story).

## Acceptance criteria

- This ticket's own PR (which bumps every manifest) shows `publish-check` running and green.
- `ci.yml`'s existing jobs (`test`, `fmt`, `clippy`) still run in full on the same PR — proves the
  workflow split didn't regress the existing gate.
- The `publish-check` run's CI run id is recorded in this ticket's build report — that id is the
  evidence used to decide on triggering the real publish.
- `publish.yml` is not exercisable until after merge (`workflow_dispatch` requires it on the
  default branch) — don't try to prove it runs pre-merge; `actionlint`/YAML validity is as far as
  this ticket can verify it, if the repo already has that check.
