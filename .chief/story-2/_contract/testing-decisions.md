# Testing Decisions

The strategy is decided in ticket 9 of `docs/design-decision-phase-1/` and is not repeated here. A good test observes what a person or a program can see: output, exit codes, and files a command leaves untouched. A check that cannot fail is not evidence, so each is shown able to fail. Expected values are written by hand and never generated by running the tool. Story 1 built the fixtures, the goldens, the spawn helper, the shell-example harness and the difference lists; this story uses them and adds what a write path needs.

Story 2 writes the user's files, so one habit is different from story 1's: a test asserts what a command left on disk as well as what it printed. "Nothing was written" is an assertion with a subject — the file's bytes, its mode, and the absence of any file the run did not mean to create — not a silence.

## What story 2 builds

1. **The round trip over a corpus** (goal criterion 1). For every document in the fixtures, a `set` of one field, then a read of every other field, compared with what it held before. No value differs. The text differs only where the design's table of losses says it may. The fixtures are extended until they carry every shape in that table — a comment, a blank line, a flow list, both quote styles, an anchor, an alias, a tag — and a shape in the table with no fixture holding it is a gap in the check, so the table is read from the design and compared with the corpus, in the same way the shell examples are read from the design.

2. **Two writers that take the same lock, tested two ways.** Running several processes one after another and finding no duplicate key proves nothing: it is the same result an implementation with no lock at all gives whenever the runs happen not to overlap. So the collision is made to happen, twice over.

   - **Deterministically, through the seam.** Two allocations run on two threads in one process against one fake file system. The fake is told to block the first writer at the instant between reading `last` and writing it back — the only instant where a lost update can happen — and to release it once the second has reached the same point. The lock must make the second wait. No timing is involved, so the test cannot pass by being lucky.
   - **Across real processes.** A shipped binary holds the namespace's lock (the same holder the signal tests need, with no test-only code in it). While it holds, `n` processes running `new` are started with a `--lock-timeout` long enough that none gives up. The holder is released only once all `n` have been started, so every one of them was waiting before the race began. Then: `n` distinct keys, `last` equal to the highest of them, `n` documents on disk, and no document written over another.

   Both are shown able to fail. A build in which the allocation reads and writes `last` outside the lock must turn both red, and that demonstration is part of the story's evidence, in the same shape as the self-tests the repository already has. A check on the write path that has never been seen red is the check most worth doubting.

   Two worktrees under `git-common` are outside this, as the goal says. What is tested there is the design's actual claim: two worktrees can allocate the same number, and `validate` reports the duplicate after the merge.

3. **That there is one lock path, proved rather than described.** Acquiring returns a value with no public constructor and no public fields; the acquire function is the only function that returns it; every function that writes takes it by reference. The proof is a compile-fail test: constructing that value outside its module does not compile, and calling a writing function without one does not compile. Each case is shown able to fail by a variant that does compile, so the test is not passing because the harness is misconfigured.

   Default: `trybuild` as a dev-dependency, chosen by the ticket that builds the lock and recorded in `.chief/project.md`. If it is not added, the property rests on the module boundary alone and nothing tests it — which is weaker, and is recorded as weaker rather than described as proof, because the signal test in a shipped binary is a test of every command only for as long as this holds.

4. **Fixtures for the four rules this story builds,** each of which turns its rule red, as the goal requires of every rule the story builds.

   - `state.malformed`: one project whose namespaces carry a state file each, with `last` as text, as `null`, negative, a fraction, and larger than typdoc can hold. Several namespaces in one project rather than several folders, so the one-folder-per-rule shape of `broken/` is unchanged.
   - `state.behind`: `last` lower than the highest number that exists, reported at `warn`, with allocation still giving the right number in the same run.
   - `state.retired`: an entry for a collection the project no longer has, reported at `warn` and stopping nothing — including a read, which is what its predecessor as a config error did stop.
   - `frontmatter.transitions`: the first fixture whose declared command is a write. It attempts a transition the schema does not allow, and asserts exit 2, the finding, and that the document's bytes are unchanged.

   Each of the three state rules also has a project where the state file is correct and the rule is silent. A rule that fires on everything passes its own fixture.

   The measurement behind decision 13 becomes a test, because it is the reason those rules report and never repair: with a key's document deleted, deriving `last` from the files hands that key out again and an existing link then resolves to the wrong document with nothing reported, where keeping the gap gives a missing-target finding from the same run.

5. **A fixture that writes is copied first.** The loader copies a fixture whose declared command is a write to a temporary directory and runs the copy. A write fixture about to run in the repository's own tree is a failure of the harness. The check is shown able to fail by a fixture that declares a write and is pointed at the tree.

6. **The write seam.** One scenario table, run twice: against the fake, and against a real temporary directory. The fake stages what a real directory will not — no space, permission refused, a rename across devices, and a stop between any two operations — and the real directory holds the fake honest about what a file system does. A power cut and a `SIGKILL` at the level of a single system call are covered by neither, and that is written down rather than left to be assumed.

7. **Signals.** A shipped binary holds a lock and is sent a real `SIGINT`, then a real `SIGTERM`. The lock file is gone afterwards; the process ended by the signal and not with an exit code, so a caller sees a signal death; a second signal arriving during the cleanup waits rather than cutting it short. The window inside the creating call is not tested as closed, because it is not closed: what is tested is that the run that meets a lock file nobody owns stops at exit 4 with the file named.

8. **What an interrupted `mv` leaves, and that the same command finishes it.** A `mv` stopped in the middle of its renames leaves the document where it was; `validate` reports the refs already rewritten as pointing at a path that is not there; running the same command again completes the move and leaves no finding. The test asserts the message names the re-run, since a recovery path a user has to deduce is not one.

9. **Temp files and leftovers.** A file whose name has the reserved shape is skipped by the walker even under a `match` of `*`; a leftover is reported at `warn` and is counted in the audit's list of entries that were not read; the accounting invariant from story 1 is extended with that count and still holds. A leftover inside a lock's scope is removed by a command that holds the lock, and a removal that fails does not fail the write.

10. **Permissions across a rename.** A document whose mode is set to something other than the default keeps that mode after a write. Owner, group, access control lists and extended attributes are not claimed and are not asserted; the test says so in its name rather than leaving the absence to be read as an oversight.

11. **Goldens for `new`, `set` and `mv`,** with the injected clock so `auto` fields have a time a golden can hold, and the assertion files hand-written as before. `mv`'s golden carries `unrewritten` and `findings`, including a move whose destination schema rejects the document, which exits 0 — the case where reading the exit code instead of the payload would be wrong.

12. **Exit codes 3, 4 and 7 produced by tests:** an `--if` that is false with nothing written, a lock held past the timeout, and each of the four destinations that already exist.

13. **The case-only move.** Source and destination compared by file identity rather than by text; on a file system that tells the two spellings apart the move is ordinary, and where it does not the move is exit 7 with the message that names the reason. The second half cannot be run here — no case-insensitive file system is available on this machine, and that is recorded in decision 12 — so it is asserted against the identity check itself rather than against a file system that behaves that way, and the gap is written down.

## The two pinned gaps, and how they close

`[number-text]` and `[empty-value]` are each pinned by a test on both sides: the binary's behaviour today, and what the design asks for. Closing one turns its test red, which is the signal to remove the entry from `KNOWN_GAPS` in the same change. Neither entry may be removed while its test still passes in its old direction, and neither test may be deleted instead of being turned round.

Closing `[number-text]` rewrites every golden that holds a number. They are regenerated by the generator, whose guard is unchanged — it writes no assertion file and has no regenerate-all — and the assertion files stay written by hand. The size of that diff is expected; a golden that changes in a way the printing rule does not explain is not.

## Differences between the design and the binary

The three lists work as story 1 built them, checked in both directions, and this story empties the write half: `new`, `set` and `mv` leave `unimplemented_commands`; 3, 4 and 7 leave `unproduced_exit_codes`; `frontmatter.transitions`, `state.malformed`, `state.behind` and `state.retired` leave `unimplemented_rules`. A rule leaving that list brings the fixture requirement with it, so the rule and its fixture land together or the suite is red.

`KNOWN_GAPS` keeps `[reverse-scope]` and `[import-anchor]`, which this story does not touch.

## The acceptance run, made by hand

At the end of the story, the round trip of item 1 is run against copies of the public `chief` and `typmem` repositories, each with a `.typdoc` folder written for the run and not committed to them, and the result goes in the story's closing report. It is not part of `cargo test`, because those repositories are not fixtures, and the suite reaches nothing outside this one. Real files enter the fixtures only after review and the public-text check (phase 1, tickets 1 and 9).
