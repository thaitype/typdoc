# Testing Decisions

The strategy is decided in ticket 9 of `docs/design-decision-phase-1/` and is not repeated here. A good test observes what a person or a program can see: output, exit codes, and files a command leaves untouched, not the internals that produce them. A check that cannot fail is not evidence, so each is shown able to fail. Expected values are written by hand and never generated by running the tool. This file says what story 1 builds; the table "Where each part is built" in ticket 9 says what the other stories build.

## What story 1 builds

1. **Fixtures.** `fixtures/valid/<name>/` and `fixtures/broken/<rule>/`, with the two coverage checks (every folder in `broken/` names a rule that exists, and every rule that exists has a fixture), the exact set of rules each broken fixture is expected to trip, `examples/` validated as a user receives them, and a loader that fails loudly outside a checkout. Every config error has an id and a fixture, `config.parse` included.
2. **Golden files** for `get`, `list`, `toc`, `refs`, `validate` and the error object, with the generator and its guard (it writes no assertion file and has no regenerate-all), hand-written assertion files, and arrays compared in the order the design declares. The read commands stamp no time, so there is no `Clock`.
3. **`run(args, deps)` with `Env`**, the lints for `Env` and for writes, and clippy over test code (`--all-targets`).
4. **The spawn helper:** an empty environment, a constant `PATH` that names the stand-in's directory and the shells' directory, a fresh `HOME`, and the ban on `Command::new` outside it.
5. **The harness for shell examples**, for sh and bash: the examples are taken from the design, each one that contains a character outside the safe set has a value declared by hand, the same example with its quotes removed must turn red against that value, it runs in a directory that holds files a star can match, a listed shell that is missing turns the suite red, and every code span of the Quoting paragraph is classified.
6. **Imports:** the five cases of finding `imports.json` with a fake `Env`, an unset or empty `${ENV}`, and `imports.absent` at `error` giving exit 2.
7. **A name a command prints is accepted by the next:** a test builds, for every document of a project with one namespace, one with several and one with an import, each string that the table under Arguments that name a document gives, passes it to `get --json`, and checks that the file is the one it started from.
8. **Coverage across all commands:** the registry of commands checked against the goldens and against the headings of the Commands section; `unimplemented_commands` and `unproduced_exit_codes` as described below; every exit code of the design's table produced by a test or listed.
9. **The accounting invariant** (contract, item 8) on every project in the fixtures.
10. **Lines and columns:** a Thai line and an emoji line, each with its expected `col`; a file with no final line ending; `\r\n` endings; a lone `\r`; a heading with nothing under it (`end` equal to `line`); the last section of a file.
11. **The rules and errors that are new in this story,** each with fixtures: `state.missing` (a file that is absent while documents exist, a file without the entry, and a new collection that reports nothing); `frontmatter.parse` (a block that is never closed, invalid YAML, a second YAML document, a duplicate key), asserting a position or its absence as the contract says; an empty block, which is frontmatter, and a file with no block, which is not; `config.schema-unpinned`, `config.vendor-missing` and `config.vendor-edited` with pinned copies made by hand; the case of paths (a ref whose case differs from the file's is `not-found`); an unresolved reference of each kind (`not-found`, `import-absent`, `bad-prefix`), with `path` and `unresolved` never together.

## Differences between the design and the binary

Three lists in code record what the design describes and the binary does not have yet: `unimplemented_commands` (`new`, `set`, `mv`, `pull`), `unproduced_exit_codes` (3 and 4, and 6 if no deterministic test is found) and, as a Default, `unimplemented_rules` (`frontmatter.transitions`). Each list is checked in two directions: everything the design names is in the registry or in the list, and nothing in a list is in the registry or produced by a test, so a list cannot be used as a way out and an entry that outlives its work is red at once. An entry carries the story expected to deliver it as a comment, which no test reads. The lists only shrink, and empty is the correct state of a finished v1.

The check on rules is the only one that is new. Ticket 9 compares the design with the registry for commands, not for rules, so a rule that the design lists and nobody builds would go unnoticed; the check reads the rule ids from the design's rule tables, as the shell examples are read from the document.

## Two acceptance runs, made by hand

At the end of the story, `validate --audit` is run on a copy of the public `chief` repository and on a copy of the public `typmem` repository (the goal gives their sizes), each with a `.typdoc` folder and local schemas written for the run. The accounting invariant is checked on the result against an independent count, and the results go in the story's closing report. They are not part of `cargo test`, because the repositories are not fixtures. Real files are copied into the fixtures only after review and the public-text gate (ticket 1, ticket 9).
