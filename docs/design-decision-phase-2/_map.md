## Destination

Story 2's fog is clear when every decision the write path needs is made and written here, so that the story's goal and contract can be written without grilling any of it again: what `new`, `set`, `mv` and `mv --renumber` promise when they succeed and when they fail partway; what a run leaves on disk when it is interrupted; how locks are taken, ordered and released; what the frontmatter round trip guarantees byte for byte; and what the write commands print. Where a decision changes what `docs/design.md` says, the design is amended in the same change.

## Notes

- **Scope of story 2**, carried over from story 1's out-of-scope list: writing anything — `new`, `set`, `mv` and `mv --renumber`, the frontmatter round trip, locks, the state file's writing, and signal handling. Remote schemas (`pull`, `vendor/`, `lock.json` as a file typdoc writes, the project lock) are story 3.
- **Story 1 only read. Story 2 writes the user's files.** A read command that answers wrongly gives a wrong answer; a write command that behaves wrongly damages something the user owns. Decisions here lean towards making a partial or doubtful write impossible rather than towards reporting it after the fact.
- **`mv` has the widest blast radius of any command in v1.** One invocation renames one file and edits every file that refers to it, in every namespace of this project and in the projects it imports, keeping each ref's written form. A half-finished `mv` leaves a repository whose links partly point at the old path and partly at the new one. Tickets 1, 2 and 3 are about that, and they come first on purpose.
- **`docs/design.md` is the source of truth** (project rule 6): to deviate from it, amend the document first. Decisions here that change it are written into it in the same change.
- **Decisions from `docs/design-decision-phase-1/` that story 2 stands on, and does not reopen:** ticket 1 (read with `yaml_serde` into typed `String` fields, behind a trait of three operations — its choice of `yaml-edit` as the writer, and the reparse guard that choice needed, are the parts story 2 reopened, in [decision 20](_tickets/20-the-frontmatter-writer.md), because no code rested on either), ticket 2 (next number = max(highest existing, `last`) + 1, written back under the lock, never reused), ticket 7 (lock rules, no takeover, exit 4), ticket 9 (the write seam lives in `deps`, `Clock` is story 2's, signals are tested by holding a lock in a shipped binary with no test code in it), ticket 13 (namespaces, and that a coded document cannot cross one except by `--renumber`), ticket 15 (one way to name a document in `--json`), ticket 22 (paths compare with their case).
- **The code as story 2 finds it.** `crates/typdoc-core/src/lock.rs` is `lock.json`, the pin file, not the namespace lock; the namespace lock has no module yet, and a second module named `lock` would read as the same thing. `Deps` holds `env` alone, so the write seam and `Clock` are both additions. `unimplemented_commands` and `unproduced_exit_codes` in the test suite hold what story 1 left undone; story 2 empties the write half of both, and an entry that outlives its work turns the suite red.
- **Open findings from story 1's review that land on the write path.** An integer past u64 in frontmatter is kept as text when read but becomes a float in `--json`, losing digits (settled by [decision 10](_tickets/10-a-number-past-u64-on-the-write-path.md), with the binary's present behaviour pinned as the known gap `[number-text]`); an invalid `body.links` `ignore` glob is dropped silently; `links::find_on_line` is quadratic in the number of `[` on one line; the cycle walk in `refs.rs` recurses and overflows the stack on a long chain. The first is a data-loss risk once a command writes frontmatter back, and the third becomes a write-path cost because `mv` scans body links.
- **The lint from story 1's ticket 29 applies to everything story 2 adds:** non-test code in `typdoc-core` may not `unwrap`, `expect`, `panic!`, `unreachable!`, `todo!` or `unimplemented!` without `#[expect(clippy::<lint>, reason = "<the evidence>")]` naming the guard, the only constructor, or the caller that checks first.
- Tickets here use the inline `Type:`, `Status:` and `Blocked by:` lines, as story 1's decision tickets did.

## Decisions so far

<!-- index: one line per resolved ticket, enough to judge relevance, zoom the link for detail -->

- [A `number` past u64 on the write path](_tickets/10-a-number-past-u64-on-the-write-path.md): the loss is not where it was feared. Decision 20 hands the write path the text the reader kept, so nothing turns a value into a number on the way to disk and the file is safe; `set` therefore writes such a number unchanged and never refuses it, since refusing would forbid a value the format holds exactly and a `string` field already carries. What is left is printing, and it is worse than lost digits: `99999999999999999999` and `99999999999999999998` both print `1e+20` and cannot be told apart, `1e3` prints `1000.0`, and `validate` calls the document entirely well. So a `number` in `--json` is printed with the digits written in the document. JSON puts no limit on them and the readers do — measured, python and jq keep a twenty-three-digit value whole and node rounds it — which moves the rounding to the reader that cannot hold it, from a value that was true when it arrived, instead of typdoc deciding silently. It is the rule the read path already runs on: nothing between the file and the caller decides what `1e3` is, and the printer was the one step that still did. The read side is fixed in this story rather than guarded around, because decision 17 has `new` and `set` print `get`'s own object, so the write commands cannot be right while it is wrong. The cost is stated: every golden holding a number changes, which is free only because nothing has been released. Comparison is not fixed by this and is not smuggled in — it is [decision 22](_tickets/22-comparing-numbers-beyond-a-primitive.md), off this story's frontier.

- [A `mv` that changes only the case of a path](_tickets/12-a-mv-that-changes-only-case.md): `mv` asks the file system whether source and destination are one file rather than comparing the text of the paths, because strings say they always differ while identity says they differ on a case-sensitive file system and are one file elsewhere — the two answers disagree exactly where the damage is. When they are one file the move is refused at exit 7 with nothing written, which is the code decision 15 made for a destination that exists, and the message says the file system does not tell the two names apart, since "the destination exists" would send the user looking for a file they cannot find. The same refusal covers the same path given twice, which POSIX would otherwise let succeed while changing nothing. Carrying the move out through an intermediate name was rejected: the file system decides what spelling it keeps, so typdoc would have to read the directory back before rewriting a single ref and then either rewrite them to something the user did not ask for or undo the move — a second mechanism through the command with the widest blast radius. typdoc never probes what a file system does in general; a probe costs a file in the user's project, can be wrong for another directory on the same machine, and answers a question nobody asked. The prototype's finding was carried across the change of mechanism in decision 7 rather than left to be rediscovered: it is the destination check, not a no-replace rename, that now refuses. The event is nameable — a repository under `/mnt/c` in WSL is on a case-insensitive file system and the design says WSL works — which is why the clear refusal is built and silence is not.

- [The `--json` shapes of `new`, `set` and `mv`](_tickets/17-the-json-shapes-of-new-set-and-mv.md): `new` and `set` print `{ "document": <document> }`, the object `get` already prints — the whole document for `new`, because the defaults and `auto` fields it filled in are exactly what the caller could not work out. Neither reports which fields the write changed, and the test that settles it is whether the value would differ for the same document reached another way: a `changed` list would, so it is a fact about the command, and the case behind the argument is served by `--if`, which decides before the write instead of reporting after it. An `--if` that is false exits 3 and prints the error object on standard error, because one total rule — zero exit to standard output, non-zero to standard error — beats a table of which codes print where, and its `details` name the condition that failed, which a caller giving several cannot otherwise know. `mv` adds `unrewritten`, the reference object taken from `refs --reverse`'s direction so the entries can be handed back to whatever reads `refs`, each with a `reason` of `imported-project`, `mention` or `links-rule-off`; and `findings`, in `validate`'s own shape, carrying what the destination's schema rejects — the field a caller branches on instead of the exit code, which decision 16 fixed at 0. No count of what was rewritten, for the same reason as `changed`, and no `complete`, because a `mv` that stops partway is an error rather than this shape, so on the success path it would always be true. `unrewritten` borrows `refs --reverse`'s order and `findings` the order findings have everywhere.

- [The single lock-acquisition path](_tickets/6-the-single-lock-acquisition-path.md): `signal-hook`, at an ordinary version requirement and not an exact pin, because it is the one candidate covering all three requirements in a single dependency and the exact pin belonged to a crate chosen despite being days old. Every command reaches a lock through one path, proved rather than remembered: a held lock is a value with no public constructor, returned only by the acquire function, and the functions that write take it, so a command cannot write under a lock it did not acquire that way — which is what makes the signal test in a shipped binary a test of every command. The handler is registered before the first lock file exists; what remains is the instant inside the creating call, where a lock file exists that the process does not yet name, and typdoc will not remove it because it has no evidence the file is its own — that window stays open, in writing, and its outcome is a stop at exit 4 whose message already names the file to delete. The handler itself only wakes a thread, since the identity check and the unlink are not async-signal-safe, and the process then ends by the signal rather than with an exit code, so an interrupted run does not look to its caller like a decision; a second signal waits for the cleanup rather than cutting it short. Every place an interrupt can land in the middle of the work was already settled by decisions 1 and 4 and by the allocation rule, and the one the ticket feared — a document written and its number not recorded — cannot happen, because the next number is the larger of the highest existing number and `last`.

- [The write seam and the clock](_tickets/7-the-write-seam-and-the-clock.md): `Deps` gains the file operations a write is built from, not `write this document`, because everything decision 4 settled — the temp file's reserved name shape, the walker skipping it, a leftover as a `warn` finding, the mode carried across, removal only under a lock — is policy that must live above the seam in the code that ships, or every test of it tests the fake instead. One function above the seam holds those rules so no command sees a temp file. The gap decision 15 left open — that `O_EXCL` does not reach a document put in place by a rename — stays open on purpose. `link` would close it, taking a name or failing where `rename` replaces in silence, both measured; but under the lock the only thing left in the window is a program that is not typdoc creating exactly that path in the microseconds between the check and the rename, an event nobody can describe, and closing it costs a state where a document has two names, with its own rule, test and sentence in the design. `new` keeps `O_EXCL` because it is one call that adds no state and costs nothing: the line is not how much protection but what the protection is paid for with. A document therefore moves with a plain rename, which cannot cross a filesystem (`errno 18`) and is not given the shell command's copy-and-delete fallback; a document whose contents are replaced is still written to a temp file and renamed over, which is not a move but the way an interrupted run cannot leave half a file. Tests use a fake in memory and a real temporary directory against one scenario table, the fake for the failures no real directory stages — out of space, permission refused, a rename across devices, a stop between any two operations — and the real one to hold the fake to what a filesystem does; a power cut and a `SIGKILL` at the system-call level are covered by neither and recorded so. The clock gives an instant and the offset to write it in, at one second, so typdoc's own formatting stays testable and a golden file can hold a time. Reads stay outside the seam, deliberately — a wrong read is a wrong answer and the next run corrects it, a wrong write damages a file and nothing does — except the three a write makes to decide what to do: whether the destination exists, an existing file's mode, and whether two paths are the same file.

- [The frontmatter writer](_tickets/20-the-frontmatter-writer.md): `yaml_serde` writes frontmatter, from the text the read path already keeps, and `yaml-edit` is not added — nothing rested on it, since story 1 only read. A write therefore rewrites the whole frontmatter block rather than editing one line. No value changes when it does: sixty-five round-trip cases, covering every literal YAML would otherwise reinterpret, odd key names and every list shape, came back exactly, so values stay promised. What goes is how the block was written — comments, blank lines, flow style, quote style, spacing — and, changing what the file means rather than how it looks, anchors, aliases and tags; the design now carries that as a table instead of the unpredictable "best effort" it had. The reason it was chosen over keeping `yaml-edit` is that `yaml-edit` has documents it cannot edit at all, turning `set` into a refusal the user resolves by hand, while it also drops tags and quote style on the edited line without the guard noticing — which was the property it had been chosen for. The trait in front of the writer stays, so the choice behind it can be revisited without touching call sites. The mandatory re-read guard does not: it existed because the writer was young and a document's own shape could defeat it, and with the reader's own crate writing text it already holds there is no event left for it to prevent — it would be that crate checking itself, over a defect typdoc could not fix and would already be reading wrongly. That typdoc assembles the block it meant to is a test at the boundary of typdoc's own code, not code that ships. The atomic write and the refusal to replace an existing file stay, because the events they prevent can be told.

- [The argument shape of `mv --renumber`](_tickets/11-the-argument-shape-of-mv-renumber.md): the destination is the flag's value, `typdoc mv WF-2 --renumber story-3`, because a bare namespace name is neither a path nor a key and a positional one would need an exception cut into a rule that has none; so `mv` takes two positionals ordinarily and one here, and `--renumber` becomes a flag that must be given a value. A destination equal to the document's own namespace is refused: carrying it out would retire `WF-2` for good while the document never moved, break every citation outside the project, and leave `validate` at exit 0 with nothing to report. The new key is printed bare on stdout as `new` does. Renumbering into another project is impossible and the design says so, because `project::namespace:key` exists for reading and invites the guess. The source's `last` never goes down: it is the highest number ever issued, not the highest that exists, and closing that gap would make `new` reissue a retired key with nothing to report it.
- [`mv` and imported projects](_tickets/2-locks-when-mv-writes-into-an-imported-project.md): `mv` does not write into an imported project, and no write crosses a project boundary in v1, so the design's one exception to "an imported project is read-only" is removed rather than given a mechanism. The refs another project holds are now among the things `mv` cannot rewrite, which decision 1 already made a reported success at exit 0; the report names the project each unrewritten ref is in, and the refs, because a count tells nobody where to go. The lock question this ticket was opened for disappears with the write, and the design says so plainly instead of leaving it to be derived. Decisions 1 and 3 were corrected where their text claimed the imported-project case occurs.
- [`mv` across collection boundaries](_tickets/16-mv-across-collection-boundaries.md): a coded document may not move out of its own collection's folder and an uncoded one may not move into a coded collection, both refused for structural reasons — a coded `match` takes `{key}` once with no globs, and a coded document moved out leaves every ref by key pointing at nothing; `--renumber` is the path that exists. A move into another collection whose schema the document fails is carried out and reported, because refusing leaves no order of steps that works and forces the user out of the tool, with `pull` as the precedent. That move exits 0, not 2: exit 2 always comes with nothing written, and giving it two meanings would leave a caller unable to tell whether the world had changed; the check travels in the `--json` payload and CI catches it with `validate`. Moving out of every collection is allowed and announced in the command's own words, since it is the one case nothing afterwards reports.
- [A write whose destination already exists](_tickets/15-a-write-whose-destination-already-exists.md): all four cases are refused and nothing is overwritten, because overwriting a user's work with no undo is the worst outcome in the tool and an atomic write makes it traceless. The refusal is a new exit code, 7, not 1: the call was correct in every part, and what to do next is choose another name or open the file that is there, which is neither fixing the call nor retrying it. The check is made under the lock and `new` creates with `O_EXCL`, so the file system enforces it. Open and recorded: `O_EXCL` does not reach `mv` or `--renumber`, which put the document in place with a rename, and a plain rename replaces silently; the rename that must not replace is a different operation from the one that completes an atomic write, and which call provides it goes with decision 7.
- [A `mv` that fails partway](_tickets/1-a-mv-that-fails-partway.md): `mv` does not promise to be all or nothing, because a file system gives atomicity one rename at a time. It prepares every temp file first and then renames in one run; the run of renames is the window that remains, and the design says it is not closed. The document moves last, always, so that the same command run again finishes the work and is its own way back, with no journal; a run that stops says so and says the command can be re-run, and `validate` reports the inconsistency until it is. Mentions, body links with the rule off, and refs held by any other project do not fail the run: it exits 0 and reports them, because `mv` promises the refs typdoc tracks and a project that needs more sets `imports.absent` to `error`. `mv --renumber` carries the same promise plus one rule: the destination's `last` is written before the document appears under its new key, and a skipped number is ordinary.
- [What an interrupted write leaves behind](_tickets/4-what-an-interrupted-write-leaves-behind.md): v1 promises the user's documents are not damaged, not that no temp file remains, because `SIGKILL` and a power cut cannot be caught. Temp files take a reserved name shape carrying the pid and a random part, and the walker skips that shape by rule before `match` is consulted, since `*` matches a leading dot and a user may write `match` `*`. A skipped leftover is a finding at `warn` and joins the entries already skipped as one audit category of things not read, which closes an accounting hole that `files.unreadable` has today. A command holding a lock may remove leftovers in that lock's scope, never by age, and a failed removal never fails the write. The mode of an existing file is carried to the temp file before the rename; owner, group, ACLs and extended attributes are not, and the design says so rather than claiming permissions are preserved. Durability without `fsync` is recorded as undecided.
- [One order for taking locks](_tickets/3-one-order-for-taking-locks.md): locks are taken in the order of the lock files' own paths, compared byte by byte as absolute paths, with the project lock first; not by namespace name (two projects can share one) and not by document path (`default` has no folder). One rule covers both lock modes and imported projects, and needs no tie-break, because two lock files that differ are two different paths. The design now states it once and the three places that disagreed refer to it. Whether one acquisition path is enforced, and by what, is decision 7.
- [The `git-common` project hash](_tickets/14-the-project-hash-in-git-common-locks.md): SHA-256 of the project folder's path relative to the worktree root, normalized to `/` with no trailing separator, truncated to 16 hexadecimal characters; a worktree that keeps the project elsewhere is a different project on purpose. A 64-bit collision makes two projects share a lock and wait, which loses nothing and is accepted knowingly. The hash is promised stable, and changing it is a breaking change. `--git-common-dir` is canonicalized before use.
- [Writing the state file](_tickets/13-writing-the-state-file.md): a file typdoc creates holds JSON with keys in alphabetical order, two spaces of indentation, `\n` endings and a final newline, because the file is committed and a conflict should mean a real disagreement; updating an existing entry still replaces only the number in place and reformats nothing. A `last` that is present but unusable — text, `null`, negative, a fraction, too large — is its own finding, `state.malformed`, because reporting a record the user can see in the file as missing sends them to restore a file that is not lost; a `last` lower than the highest existing number passes silently today and becomes `state.behind` at `warn`, since allocation still gives the right number but a record nobody checks is how a wrong one comes to be trusted. Neither is repaired by typdoc: deriving `last` from the files is the obvious fix and it reissues a retired key, measured — delete `WF-3` and derive, and the next `new` hands `WF-3` out again so an existing link resolves to the wrong document with nothing reported, where keeping the gap gives `link target missing: WF-3.md` from the same run. An entry for a collection the project no longer has is kept and is `state.retired` at `warn`, not the config error it is today, which stops every command including reads and offers deleting the only record that those numbers were issued; `config.state-uncoded` narrows to a collection that exists whose schema has no code. No command ever removes an entry. `mv --renumber` writes one state file, the destination's: `last` is the highest ever issued and never goes down, so the source has nothing to write, and decision 1's order is then the whole of the ordering.
- [Signal-handling crates](_tickets/5-signal-handling-crates.md): facts gathered, choice still open. `signal-hook` 0.4.4 is the only candidate that covers re-raising the signal (`low_level::emulate_default_handler`), moving the cleanup off the handler (`Signals`) and running without a runtime, in one dependency; `nix` 0.31.3 is the runner-up and `ctrlc` is ruled out by the re-raise requirement. Registering before the lock is created is possible with all of them, so that gap is closed by the order of the calls, not by the crate. Ticket 6 makes the choice.

- [Comparing numbers no primitive holds](_tickets/22-comparing-numbers-beyond-a-primitive.md): a real decision, but about the query path, not the write path, so it is off this story's frontier and blocks neither the goal nor the contract. Measured: two documents whose `count` differs by one in the twentieth digit compare equal, so `count>...998` returns nothing, and `validate` reports nothing about either. Opened by decision 10, which fixed the printing and deliberately left the comparison alone.

- [How to resolve a merge conflict in a state file](_tickets/19-state-file-merge-conflicts.md): written as guidance in `docs/projects.md`, not as a rule in the code — take the higher `last`, never a side, and never revert the file. The damage from taking the lower side is invisible until a key whose document has gone is handed out a second time, and then nothing reports it. Open, nothing to decide.

## Not yet specified

- The text (non-`--json`) output of `new`, `set` and `mv`. The design shows `new` printing the bare key on stdout and says nothing about the other two.
- `--lock-timeout`: which commands accept it, and whether giving it to a command that takes no lock is bad arguments or is ignored. The design names the flag once, with a default of 5 s, and never says where it is accepted.
- The retry schedule behind "retries with backoff": whether the shape of the backoff is promised, and whether a caller can tell a timeout from a lock that was never contended.
- How `--set k=v` is parsed on the write path: the escape rules for a comma inside an array value, an empty value, a value that looks like a number, and whether `k=` removing a field is available to `new` as it is to `set`.
- Whether `set` may write a field that no schema in scope defines. Unknown fields are kept when read and reported by a rule; whether a write may create one is not stated.
- The order of filling defaults, filling `auto` fields, validating and taking the lock in `new`. The design gives the steps in one sentence but not which of them happen inside the lock.
- Distribution and versioning of the tool itself, and whether the suite must run from a published package. Unchanged from phase 1, blocking nothing here.
- Parked, blocking nothing and not raised again until someone takes it up: a macOS runner, and running the public-text check in CI or a hook.

## Out of scope

<!-- ruled beyond this story's destination — closed, never graduates -->

- Everything story 3 owns: `pull`, the fetch adapter, `vendor/` and `lock.json` as files typdoc writes, and the project lock that guards them. The one place they touch this story is the order in which a project lock and a namespace lock may be held, which the design already fixes and ticket 3 records rather than reopens.
- A command that deletes a document. v1 has nine commands and none of them deletes one; "a number is never reused after its document is deleted" describes a file removed by other means, not a command.
- Everything on the design's own "Out of scope for v1" list: editing body sections, SQL queries, saved query aliases, multi-hop ref traversal, imports of imports.
- Any release, packaging or distribution of typdoc.
- A claim that macOS is supported. Ticket 12 decides what a case-only `mv` does; it does not turn the code written for macOS into a supported platform, which needs a run on macOS that nobody has made.
