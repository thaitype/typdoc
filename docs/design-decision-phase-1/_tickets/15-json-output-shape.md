# 15: What does `--json` print on success?

Type: wayfinder:grilling
Status: claimed
Blocked by: 14

## Question

The design gave a shape for some commands and not for others: `get` "returns frontmatter plus" six names, `list` returns an object per document without saying what holds them, `toc` gives the shape of one heading, `refs` gives nothing, and `validate` returns "the summary and every finding". The `--json` output is what a program reads, and it is pinned by golden files, so the general rule, the shape of each command's output and whether each array has an order have to be decided together and written in one place in the design.

## Answer

Decided so far (the shapes of `toc`, `refs` and `validate`, and the order of their arrays, follow in this ticket):

1. **Every command prints an object with a named field for its result, never a bare value.** The reason is the failure this project exists to prevent: a wrong answer that looks right. `typdoc list --limit 20 --json` printing an array of twenty documents cannot say whether there are twenty matches or more, and a bare array has no place to put that fact. Adding a field beside a bare array later would change a shape people already read. Rejected: bare values (shortest to use with `jq`, but silent about truncation). Rejected: a single envelope such as `{ "result": ... }` around everything, because the exit code already says whether to read the result on standard output or the error on standard error, so the wrapper adds nothing.
2. **`list` reports `total` as well as `truncated`.** `truncated` alone tells the caller that some of the result is not visible but not how much, and the only way left is to run the query again without a limit, which may bring back an unknown amount. For a tool whose main users are programs, that is the difference between deciding and guessing. `truncated` is true exactly when `total` is larger than the number listed, and a test asserts that they agree.
3. **What `total` costs is a decision, not a side effect.** A `list` that reports `total` has to filter every document, so it cannot stop once `--limit` documents are found. The index is built on every run in any case, but filtering by frontmatter means reading the frontmatter of every candidate, and that part is new. Not measured. If the cost becomes too high it is a matter for the scale question on the map, and it is not a reason to ship a less useful shape now.
4. **A document has one shape, wherever it appears.** `get` and each member of `list` use the same object, with the same keys and the same nesting; only the wrapper differs. Otherwise a caller writes two readers for one thing. The frontmatter is held in `fields`, apart from `path`, `key`, `code`, `collection`, `schema` and `namespace`, because a frontmatter field that is not in the schema is kept and can have any name, `path` included; merged at the top level it could overwrite one of those.
5. **Consumers must ignore fields they do not know**, stated once in the design under JSON output and covering the error object too. The value of the first decision is that fields can be added without breaking the shape, and that is true only if a consumer is told not to fail on a field it has not seen; the first strict reader would otherwise break at the first addition.

6. **Commands are of two kinds, and the design says so as a rule.** A command whose result is a verdict on the project (`validate`, and `pull --check`) prints the verdict on standard output whether or not it is favourable, and signals it with the exit code: the findings are the result, and exit 2 means some of them are errors. A command that does something prints its result on standard output when it succeeds and an error object on standard error when it cannot. It is written as a rule, not as an exception for `validate`, because an exception makes every future command argue again about which side it is on; the rule answers by asking whether the result is a judgement about the project or the outcome of an action. The first wording in the design, that a failure prints an error object, could not answer for `validate`, whose exit 2 is a result and not a failure, and it was replaced by the rule, not amended.
7. **A report must not read as more than it checked.** The summary of a verdict states what was checked (the namespaces, the number of documents, and the paths or keys when the command was given any), so that `validate WF-3` reporting no findings cannot be read as a clean project.

8. **Config errors and the report of `validate`.** A config error that makes checking impossible prints the error object on standard error and exits 2, and one that leaves checking possible is a finding in the report. It is written as a criterion in the design (does it make checking impossible?), not as a list of ids, so that whoever adds a config error answers it for that error; the same shape as the criterion that decides which rules need a fixture in `broken/`. Applied to the design as it was: the collection files, the schemas, the pins, the namespace folders and `config.json` are shared by every document, so their errors stop the command. `config.state-orphan` (a leftover file in `state/`) and `config.state-uncoded` do not prevent any document from being checked, so they are findings. The design did not say that they stop the command; they stopped it only because a config error was treated as an error object. Stopping a whole run for one leftover file is out of proportion, and under the old treatment it would have removed the whole project's report of defects.
9. **The error object carries every config error that can be determined, and says when it cannot.** `validate --audit` exists to say what has to be fixed before adopting typdoc; a loader that stopped at the first would make it fix one and run again, which defeats it. Where the rest cannot be known (a `config.json` that cannot be parsed, an unknown `version`), the list ends there and the object says `"complete": false`. This is not a detail left to the contract: it is what makes the cost of an error object in the adoption loop acceptable. The design had no id for a `config.json` that cannot be parsed (only `config.collection-parse`), so `config.parse` is added.
10. **The two forms in the adoption loop are a change of state, not an alternation.** While the config cannot be loaded, `validate` prints the error object; once it loads, it prints a report every time from then on. The design says so next to the description of a typical adoption.
11. **The earlier idea of a summary field for a namespace that could not be checked is dropped.** With a broken config there is no report at all, which is louder than a report that says what it did not check and can be misread by someone who looks only at the number of findings. The structure makes the wrong form impossible, and a field the reader has to remember to look at is weaker.

12. **A finding has one shape wherever it appears**, in the report of `validate` and in the `details` of an error object, the same rule as for a document: a caller writes one reader. The design used two vocabularies for one thing (`path:line:col level message rule` in the report, `doc`, `field`, `rule` and `file` in the error object), and `doc` in the example was a key while `file` was a path. Now there is `path`, and `namespace` and `key` beside it when the file is a document. The example in the design also gave the rule as `transitions`; the rule is `frontmatter.transitions`, and the example is corrected.
13. **`path` is relative to the project folder, the folder that holds `.typdoc`,** for documents and configuration files alike. The design never said what a path was counted from. It is unique across namespaces and can be opened as it stands, which a path relative to a namespace folder is not in a project with several. The text output prints the same path, and every path `validate` prints is written this way, because a reader of the text hits the same ambiguity across namespaces as a reader of the JSON, and two meanings of one word are what this decision removes.
14. **`namespace` stays beside `path`, and the reason is recorded.** The namespace `default` has no folder of its own (`match` counts from the folder that holds `.typdoc`), so its documents' paths contain no namespace name and none can be recovered from them. It looks redundant only in a project with several namespaces; dropping it would break the project with one, which is the commonest.
15. **A finding never locates a file of an imported project.** Every rule that produces a finding (a missing ref target, a target of the wrong schema, an absent import, a duplicate key) is about a document of the project being checked; the design validates refs across projects without validating the documents of the other project. Written as a rule so that it does not have to be inferred. It says nothing about `refs --reverse`, which returns documents from imported projects as results and not as findings; how a document of another project is named there is settled with the shape of `refs`.

Open, found while checking this and not decided here: which file a schema-drift finding (`validate --schemas`) names, since it concerns a field used through a ref into an imported project and the design does not say where the use is; and what a path given as an argument is counted from, since a `path` printed by one command has to be accepted by the next, and the design says only that the project is found by walking up from the current directory or from a document path given. An agent that runs above the project, the case `TYPDOC_DIR` exists for, cannot pass on a project-relative path unless the design says how it is resolved.

16. **The report of `validate`** is `{ "summary": ..., "findings": [...] }`. The summary holds `scope` (`all`, `paths` or `schemas`), `strict`, `checked` (`namespaces`, `documents`, and `paths` for `scope: paths`) and `findings` (the count per level). `scope` is the structural answer to a clean-looking partial report: the empty findings of a check of one document and of a check of the whole project read the same without it. `strict` does the same job for the counts. The counts are those after the rule levels are merged and after `--strict` raises warnings, so they agree with the exit code, and `strict` is in the summary so that fifteen errors are not read against a configuration file that calls the same findings warnings.
17. **The output promises only what a caller cannot work out from what it is given.** Every field promised must stay true for as long as the version does, and a count of findings per rule is computable from `findings`. Rejected: a per-rule count in every report. Rejected: leaving `scope` out so that the caller infers it from the arguments it sent, because a caller that receives the result of a hook or of CI did not type the command.
18. **`checked.paths` holds the resolved `path` of each document, not what the user typed.** Then it and `findings[].path` speak one language and can be matched; a key such as `WF-3` in one and a file path in the other would be two vocabularies where they had just been joined. The arguments of `validate` are keys or paths of documents, in any mix (the design's synopsis takes `<key|path> ...`). A key that is ambiguous across namespaces stops the command with exit 1, and an argument that names no document with exit 5, in both cases before any report exists and never as a finding.
19. **The order of `findings` is guaranteed** and a golden file compares it as it is, not sorted first (ticket 9). It is ordered by `path`, `line`, `col`, `rule` and `message`. It differs from the order of `list` on purpose: findings are ordered by position in a file and documents by key, whose number is compared numerically, and making the two agree would let the order of findings depend on the numbers in keys. Default: the design says only that `path` is compared lexicographically; it is taken as the bytes of the UTF-8 path, which is what comparing Rust strings does. Not verified against any other definition.

Open, not decided here: what `validate` does when `--schemas` or `--audit` is combined with arguments (the design gives no rule).

20. **`--audit` adds an `audit` object, and findings carry `collection`.** The text form of an audit is a table of counts per collection and rule. The raw material of it is two things a caller cannot work out: the collection of each finding, and the number of documents per collection (a clean document produces no finding). So a finding gains `collection`, and `audit.collections` holds the document counts; the table itself is computable from those and is not in the JSON. `audit` also lists `uncollected` and `no_frontmatter`, sorted like paths. The files in the two lists are disjoint: a file in no collection has no schema saying what its frontmatter should hold.
21. **The summary of an audit says how much is outside `findings`.** `summary.audit` is true and `summary.unreported` counts the two lists. Only saying that the mode is on says nothing about a heap the reader has not read. These counts can be worked out from the lists, so they are the one exception to the rule that the output promises only what a caller cannot work out; the exception is for values in the summary whose job is to stop other numbers being read wrongly, the job of `scope` and `strict`, and the field is named for its purpose (`unreported`), not for its type.
22. **The two modes treat a file with no frontmatter differently, on purpose.** `validate` evaluates it against its schema and each missing required field is a finding; `--audit` lists it in `no_frontmatter` and evaluates nothing, so that a directory of plain notes does not bury every other defect. It is a difference of mechanism and is written into the design as one. Rejected: expressing the two lists as findings with rules made up for them (`audit.uncollected`, `audit.no-frontmatter`): the rules would have no level to set, no line or column, and no way to be switched off, and they would enter the registry of rules for which ticket 9 requires a fixture each. Rejected: a table of counts per collection and rule in the JSON, since it is worked out from `collection` on each finding.
23. **A block that is present but empty is frontmatter; a file with no block is not.** The design defined neither. An empty block is a document that declares itself and has no fields yet, and it is validated like any other; treating it as absent would put a document that lacks every required field among the files that are not typdoc's, with no signal, which is a wrong answer that looks right. A file has frontmatter when it begins with a `---` line that opens a block.

Open, found while checking this and not decided here: which rule reports frontmatter that has a block but cannot be parsed (a block that is never closed, YAML that does not parse). The design lists no rule for it, and every rule needs a fixture.

24. **There is one way to name a document, and it is written as a rule.** `path`, `namespace`, `key` when there is a code, and `project` when the document belongs to an imported project. A document object, a finding and a reference are that name plus what each needs: a document adds `code`, `collection`, `schema` and `fields`; a finding adds `rule`, `level`, `message` and a position and never has `project`, since it is always in this project; a reference adds `field`, `written` and a position. It is one identity used in three places and not three shapes. Relying on using the same field names by care would be the way the shapes drift; the rule is what stops it. A new shape adds to the name and never renames part of it. It sits under JSON output, not with each command. It also settles that a `list` that reaches an imported project (the design allows `--namespace 'chief::*'`) carries `project` on its documents, and `path` is relative to the folder of the project the document belongs to.
25. **`refs` prints a small reference, not a whole document.** `{ "document": <name>, "direction": "out" or "in", "refs": [...] }`, each reference being the name of the other end plus `field`, `written` and, for a body link, `line` and `col`. `refs` is a question about a graph; a caller that wants the fields of the other end has `get`. Rejected: a whole document object for the other end, which would carry every field of every document, and cannot represent a ref that does not resolve, since there is no document to put there. Rejected: text identities like `chief:WF-7`, which make the caller parse what `--json` is there to spare it. `written` cannot be worked out from the other end, and `mv` needs it to keep the form a ref was written in. `col` is added to `line` for body links because a line can hold several links.
26. **A reference that does not resolve says why.** No `path` and an `unresolved` reason: `not-found` (the place the ref names is present and the target is not), `import-absent` (the import is not on this machine, which `imports.absent` reports) or `bad-prefix` (the prefix names nothing, or names a project with several namespaces without saying which). The absence of `path` alone hides a difference between a broken link and a machine that has not been set up, which are different problems with different fixes; both would look the same, and so would a present import with a missing file if `project` alone told them apart. This is the same shape as the missing state file, which was decided earlier: never having existed and having gone missing must not look the same. `path` and `unresolved` are mutually exclusive, and a test asserts that. The design lists no other reason; a further one is added to the set when a rule needs it.
27. **`--field` filters and does not change the shape.** The design gave `--field f|$body` no meaning. It keeps the refs held in that field, in both directions; with `--reverse` it is the field of the document that holds the ref, since that is where the ref is written. `direction` already covers `--reverse`.
28. **The order of `refs` is guaranteed.** For `out`: the fields in the order they appear in the document, then `$body` by position, and values within a field in the order written. For `in`: the documents that hold the refs (this project first, then imported projects by alias, each by `path`), then as for `out`. A golden compares it as it is.

Consequences for the tests (ticket 9): `config.parse` needs a fixture in `broken/` like every config error; a fixture for `config.state-orphan` asserts a finding in the report and exit 2, not an error object; and one fixture asserts `"complete": false` for an unknown `version`.

The design has a new section, JSON output, holding the rule, the document and the shapes decided so far. Each further shape and the order of each array is added to that section, not to the command that prints it, so that the shape and the order of an array stay in the same place (ticket 9 ties them together through the golden files).

Already decided elsewhere and not reopened: `list` sorts by `--sort` and then in key or path order, with `key` compared by code and then numerically (`WF-2` before `WF-10`) and `string` and `path` compared lexicographically (Sorting under `list`).
